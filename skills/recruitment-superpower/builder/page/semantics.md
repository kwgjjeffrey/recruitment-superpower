# Build a page that people and Agents operate together

The useful Omni pattern is a view as `params → returns`, derived from the real controlled UI. Here the runner's `PageContext` owns that contract. There is no separate Agent form, DOM scraper, hand-authored semantic file or extra state registry.

1. Read the registered API's actual contract before choosing inputs and outputs. Schema cannot make an invented API field real. `context.api` uses the current viewer; frontend orchestration stays in the page.
2. Declare the view in `src/page.schema.ts`. Import `PageSchema`, `Params` and `Value` from `@recruitment/page/schema` and `object()` from `/portable`. Use `as const satisfies PageSchema` and `object()` so `Params<typeof view>` and `Value<typeof view.returns>` infer types. Business meaning belongs in `description`/`semantic`; labels, widgets and placeholders belong in `ui`. Include stable record IDs in observations even when their columns are hidden.
3. Compose `AutoObject` from `params` and `AutoTable`/`AutoRead` from `returns`. A field's type, constraint and visible meaning now have one source. `ui.widget:'hidden'` hides a control/column without hiding its data from the Agent. A hidden input is still an operable parameter; do not use it for a secret or unavailable capability.
4. User changes go through `context.accept(patch)`; Agent calls reach the exact same function. Validation rejects the whole patch before mutating state. Omitted fields stay unchanged, nested objects merge, arrays replace, `null`/empty string restore the field's default. `resetOnChange:['page']` resets pagination when another filter changes. Never silently clamp or coerce an Agent's invalid value.
5. For reads use `usePageQuery(context, load)`. Keep `load` stable with `useCallback`. It subscribes to the runner, clears stale results while loading/on failure, ignores late responses/unmounts, validates and projects the loaded API response, and gives the exact same projection to React and `provide`. Extra API properties are excluded; missing/wrong declared fields fail visibly. Retry explicitly repeats a read. Do not put mutations in this hook.
6. Derive semantics during check/build. `npm run semantics --silent` prints the canonical compact publication; `.recruitment/semantics.json` stores it for review. Vite emits that same generated publication inside `dist/page.json`, beside MF's own manifest. Do not maintain a second YAML or edit compiled metadata.

`description` explains business meaning: “Minimum years of professional experience; zero includes all candidates,” not “number input.” Describe units, identifiers, clearing and value formats where they affect use. Enumeration labels explain values; controls submit stable typed values, not labels. Presentation-only details stay out of published semantics. Runtime results contain only actual loaded data, never a guessed summary or echoed request pretending to be a result.

The starter's optional availability filter demonstrates an API adapter: its clear value is `''`, but the API accepts only nonempty enum members, so `load` omits that query key when clear. This mapping belongs in one loader, shared by human and Agent requests.

Runner v1 supports one `main` view's parameters and read observations. Build fails if a page advertises form actions, extra views or host navigation that the runner cannot execute. Structured params must be explicitly excluded from the scalar URL query using `query`; use the same in-memory accept state. Do not publish unsupported capabilities to make a page appear semantics ready.

Build checks prove schema validity, defaults, parameter references, supported control dispatch, option/value agreement, reviewed component sources and TypeScript. They cannot prove a business description is truthful or a custom layout renders every declared return field. Verify that in a browser with the real API: manual edit → observed result; Agent edit → visible control/result; invalid patch → no change; no matches; API error/retry; reload. Test dropdown keyboard/Escape/focus and narrow layouts for the controls used. Write flows require actual save/reopen validation and runner support, not an invented `action` parameter.

For a main-view SQL visualization, `vizView(definition)` derives the canonical params/returns from the same Omni declaration rendered by `Viz`. Do not maintain a second result schema or publish chart state separately. A main view currently owns one `Viz`, containing any number of configured blocks.
